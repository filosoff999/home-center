# Home Center 0.13.0 — Intent Planning

## Назначение

Home Center 0.13.0 поддерживает декларативное планирование инфраструктуры. Администратор или интерфейс Home Center описывает требуемый результат, а система преобразует его в закрытый детерминированный план действий.

Планирование не выполняет изменения инфраструктуры. Исполнение инфраструктурных операций через Intent API в версии 0.13.0 отключено.

## Базовый поток

1. Принимается закрытый `Intent Request`.
2. Проверяется аутентифицированная административная сессия.
3. Поле `actor` запроса сопоставляется с владельцем текущей сессии.
4. Policy Engine проверяет точное разрешение для выбранного intent-типа.
5. Проверяются параметры и обязательные ограничения безопасности.
6. Формируется детерминированная последовательность plan-only шагов.
7. Для Storage и Virtualization план дополнительно сверяется с доверенным Resource Snapshot.
8. Для прошедшего preflight ресурсного intent Home Center детерминированно выбирает подходящий узел или пару узлов и прикрепляет placement metadata к будущему create-шагу.
9. Для потенциально опасных операций в плане фиксируется необходимость подтверждения.
10. При нарушении policy, safety или resource-инвариантов возвращается состояние `blocked` без исполнительных шагов.

## Intent API

Аутентифицированное планирование доступно через:

`POST /api/v1/intents/plan`

Запрос должен соответствовать `home-center.intent-request.v1`, использовать только режим `plan` и проходить same-origin проверку для браузерного доступа. Ответ соответствует `home-center.intent-plan.v1` и имеет состояние `planned` или `blocked`.

API не принимает пароли, токены, секреты, приватные ключи или учётные данные в параметрах intent. Такие запросы отклоняются без помещения секретного значения в ответ или журнал планирования.

## Resource-aware preflight

Для intent-типов `storage.share.create` и `virtualization.workload.create` Home Center использует только доверенные факты из `home-center.resource-snapshot.v1`. Клиентский запрос не может объявить свободные CPU, RAM или disk-capacity самостоятельно.

План блокируется, если кластер не готов к планированию или доступных ресурсов недостаточно. Возможные причины включают:

- `cluster_resources_not_ready`;
- `insufficient_cpu_capacity`;
- `insufficient_memory_capacity`;
- `insufficient_storage_capacity`;
- `insufficient_combined_capacity`.

Для HA-запроса требуемая ёмкость должна быть доступна как минимум на двух готовых узлах текущего двухузлового deployment profile. Для VM/LXC один и тот же допустимый узел должен одновременно удовлетворять требованиям CPU, памяти и диска.

Resource-aware preflight ничего не резервирует и не изменяет. Его результат способен только оставить уже допустимый plan-only план без изменений либо заменить его на `blocked` без шагов выполнения.

## Placement planning

После успешного resource preflight Home Center выбирает физическое размещение будущего ресурса. Placement остаётся провайдер-независимым: в плане фиксируется идентификатор выбранного Home Center node, а не команда конкретному гипервизору или storage backend.

Для файлового хранилища используется стратегия `storage-headroom-v1`: подходящие узлы ранжируются по относительному запасу свободного storage после учёта требуемой ёмкости.

Для VM/LXC используется стратегия `balanced-headroom-v1`. Для каждого подходящего узла рассчитывается относительный остаточный запас CPU, RAM и disk-capacity. Сначала максимизируется минимальный запас среди трёх ресурсов, затем суммарный запас. При полном равенстве используется стабильный порядок имени и node ID.

HA placement выбирает два разных готовых узла, каждый из которых самостоятельно удовлетворяет требованиям intent.

Placement добавляется только в plan-step будущего создания ресурса и соответствует `home-center.placement.v1`. В нём обязательно фиксируется:

- выбранный node ID или два node ID для HA;
- стратегия выбора;
- ссылка на тип доверенного Resource Snapshot;
- `reservation_created=false`;
- `production_mutation_enabled=false`.

Placement не резервирует CPU, RAM или storage, не блокирует scheduler и не обращается к гипервизору. Это только детерминированное решение планирования.

## Поддерживаемые intent-типы

### `node.drain`

План безопасного вывода узла в обслуживание. План блокируется при небезопасном quorum или риске потери обязательных сервисов.

### `storage.share.create`

План создания файлового хранилища с параметрами ёмкости, SMB/NFS, HA и опциональной политикой резервного копирования. Перед возвратом `planned` проверяется доверенная доступная storage-capacity и выбирается подходящее размещение.

### `virtualization.workload.create`

Провайдер-независимый план создания VM или LXC. Home Center описывает требуемые CPU, RAM, диск и HA без привязки Core к конкретному гипервизору. Перед возвратом `planned` проверяется, что требуемый набор ресурсов совместно доступен на подходящем узле или узлах, после чего в план добавляется placement metadata.

### `module.install`

План установки Market-модуля. Если разрешения модуля не подтверждены, intent блокируется до формирования исполнительного шага.

## Контракты

- `home-center.intent-request.v1`
- `home-center.intent-plan.v1`
- `home-center.intent-step.v1`
- `home-center.placement.v1`
- `home-center.resource-snapshot.v1`
- OpenAPI `home-center-intents.v1`

Контракты закрыты для неизвестных полей верхнего уровня. Размеры и форматы идентификаторов и параметров ограничены.

## Инварианты безопасности

- только режим `plan`;
- production execution отключён;
- доступ только для распознанной локальной или AD административной сессии;
- заявленный `actor` обязан совпадать с аутентифицированной сессией;
- browser POST проходит same-origin проверку;
- Policy Engine работает по default-deny модели;
- resource preflight использует только доверенный Resource Snapshot;
- отсутствие или повреждение доверенных resource-фактов блокирует ресурсный intent;
- resource preflight не создаёт новые шаги и не может ослабить решение Policy Engine;
- placement выполняется только после успешного preflight;
- placement не создаёт reservation и не выполняет infrastructure mutation;
- placement metadata добавляется только в уже существующий create-plan step;
- порядок шагов строго последовательный и детерминированный;
- blocked-plan не содержит шагов выполнения;
- Intent Engine, Resource Preflight и Placement Planning не предоставляют сетевой, файловый или process-execution surface;
- операции, которые требуют отдельного разрешения на исполнение, помечаются `execution_requires_approval`.
