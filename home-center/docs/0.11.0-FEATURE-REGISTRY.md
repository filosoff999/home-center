# Home Center 0.11.0 Feature Registry

Status: **ACTIVE DEVELOPMENT**

## HC-124 — Market Module Supply Chain Foundation

### Increment 1 — admitted now

- `ModuleManifest v2` canonical JSON contract;
- bounded duplicate-key-rejecting JSON loader;
- fail-closed semantic validator;
- exact module ID and semantic version;
- Home Center compatibility interval;
- dependency/conflict consistency;
- capability and resource-scoped permission declarations;
- bounded action metadata without executable command/path fields;
- network, storage and health declarations;
- backup/restore coverage rules;
- reversible install/upgrade metadata;
- remove semantics that preserve data;
- exact artifact digest, byte size and signed-provenance identity;
- positive and security-negative tests.

### Increment 2 — admitted now

- closed `module-provenance.v1`, module DSSE envelope and publisher trust-policy contracts;
- canonical provenance payload with exact module, normalized manifest, artifact and source identity;
- ECDSA P-256/SHA-256 public-key fingerprint and threshold verification;
- active/retired/revoked publisher key states and manifest-declared signer bounds;
- exact artifact SHA-256 and byte-size verification before any filesystem mutation;
- bounded tar+gzip structural validation with traversal, link, device, duplicate and unsafe-mode rejection;
- deterministic object key `sha256/<prefix>/<digest>/artifact.tar.gz`;
- atomic no-overwrite staging with `O_NOFOLLOW`, `O_EXCL`, hard-link publication and fsync;
- idempotent replay only when the existing object's exact bytes match;
- no network acquisition, extraction, activation or lifecycle execution.

### Increment 3 — admitted now

- closed module-admission request and admitted-result contracts;
- exact Home Center version, operating-system and architecture compatibility;
- local capability satisfaction over an immutable caller-supplied snapshot;
- deterministic dependency-first ordering;
- required and optional dependency interval validation;
- installed modules may satisfy dependencies but are never changed;
- ambiguity, incompatible shared constraints, cycles and bidirectional declared conflicts fail closed;
- permissions are aggregated only as review input and are never granted;
- production activation is fixed to disabled;
- no filesystem, process, network, topology, orchestration or lifecycle authority.

### Increment 4 — admitted now

- closed permission-review and no-pending-status contracts;
- deterministic review identity bound to exact canonical review contents;
- aggregate admission/review permission count fixed to the published 128-item contract limit;
- exact permission attribution to selected modules and typed actions;
- highest declared action risk with fail-visible `unclassified` permissions;
- bounded review size and generic non-echoing failures;
- authenticated read-only status and same-origin preview API;
- Russian Web UI `Модули` view with safe DOM text rendering;
- no persisted decision, permission grant, approval or activation endpoint;
- no artifact, lifecycle, privileged-helper, topology or production authority.

### Increment 5 — admitted now

- closed acknowledgement request, record, result and actor-scoped list contracts;
- full admission request is recomputed and exact review identity must match before persistence;
- explicit `permissions-reviewed` intent with bounded actor-scoped idempotency;
- server-controlled 15-minute expiry and same actor/module-version-scope supersession;
- HMAC-protected SQLite records and readiness integrity verification;
- authenticated same-origin create, actor-scoped item read and recent-history API;
- Russian Web UI acknowledgement history with safe text-only rendering;
- stable but non-consumable lifecycle handoff reference;
- no authorization decision, permission grant, lifecycle execution or production activation.

### Increment 6 — admitted now

- closed module install lifecycle preview request, blocked plan and no-pending-status contracts;
- actor-scoped lookup and exact active acknowledgement/review/scope/TTL binding;
- deterministic admission and permission-review recomputation before planning;
- dependency-first typed install steps sourced only from validated manifest actions;
- declared readiness/liveness postconditions and backup contracts per module;
- exact reverse-order rollback plan with mandatory data preservation;
- fail-visible preflight blockers for artifact publication, authorization, executor and placement;
- authenticated same-origin preview and read-only status API;
- Russian Web UI lifecycle boundary with safe text-only rendering;
- no acknowledgement consumption, authorization, artifact mutation, persistence, execution or production activation.

### Deferred increments

- topology-aware placement and multi-node orchestration planner;
- acknowledgement consumption and authorization inside a future lifecycle state machine;
- persisted install/update/rollback/disable/remove state machine and executor;
- module runtime identity and isolation;
- reference stateful module acceptance.

Deferred items require separate reviewed vertical slices. Neither the manifest contract nor the admission plan can execute or install anything. Parallel 0.12 password-management work remains independent and is not a dependency of this increment.

## Cross-release rules

- `release/0.10.0` continues independently;
- stable `main` is not moved by this development start;
- 0.10.0 changes enter 0.11.0 only through explicit compatibility review;
- 0.11.0 changes are not backported automatically;
- no production deployment before the complete 0.11.0 release gates pass.
