# Home Center 0.12.0 Development Baseline

Status: **DEVELOPMENT STARTED**

## Lineage

- release branch: `release/0.12.0`;
- first implementation branch: `feature/0.12.0-local-admin-password-rotation`;
- development predecessor: `release/0.11.0` at `a12a9031eb8b3c6e7824408754d485820b76ebcb`;
- stable `main` remains independent.

The 0.12.0 line inherits the production-inert Core and Market supply-chain boundaries of 0.10/0.11. It does not authorize deployment of unfinished 0.11 or 0.12 code.

## First vertical slice

The first slice implements node-local administrator password change:

- authenticated local-admin-only API and Web form;
- mandatory current-password verification;
- closed policy: at least 8 characters, one letter and one decimal digit;
- fresh random salt and scrypt verifier for every accepted change;
- fixed-path root helper operation over the protected Unix socket;
- secret request path excluded from helper request hashing, history, stdout and stderr capture;
- prevalidated atomic replacement with a durable local rollback copy;
- interrupted-transaction recovery and runtime verifier reload;
- secret-free audit result and policy metadata.

## Second vertical slice

The second slice implements recovery when the current local administrator password is unavailable:

- effective-root and physical-console presence are mandatory;
- SSH pseudo-terminals, redirected input/output and mixed TTY descriptors fail before a password prompt;
- the operator must repeat a one-time, non-secret confirmation phrase;
- the new password is entered and confirmed only through non-echoing `getpass` prompts;
- the reset reuses the node-local atomic credential transaction and the normal password policy;
- a success event is committed to a root-only, bounded, schema-closed hash chain before rollback cleanup;
- evidence failure rolls the credential back, while evidence contains no password, salt, verifier or derived secret;
- the Web runtime reloads the validated verifier on the next local login.

## Third vertical slice

The third slice completes the two-node password transaction:

- only the leader may coordinate an authenticated administrator request;
- the standby validates the current password and new-password policy before any node changes;
- the standby commits first and passes three bounded login canaries separated by a fixed soak interval;
- the leader commits only after the standby soak succeeds;
- each helper independently creates a fresh salt and scrypt verifier from the in-memory password;
- a changed intent token, concurrent transaction or invalid phase fails closed;
- every phase is durable in the local transaction ledger and HMAC audit chain without password-derived material;
- a confirmed failure compensates in reverse order, while an ambiguous transport or restart outcome becomes `recovery_required`;
- the peer surface is one closed mTLS path with typed prepare, commit, canary, rollback, status and finalize commands.

## Explicitly deferred

- release promotion and production rollout.

## Safety boundary

No caller-controlled path, command, shell, environment variable or remote-execution secret transport is introduced. Peer password material exists only in bounded mTLS request memory and is never durable. The helper accepts only compile-time credential actions and one fixed credential path. Production remains unchanged until the complete 0.12 acceptance cycle and separate rollout authorization.
